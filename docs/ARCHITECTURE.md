# Архитектура

## Компоненты

| Модуль | Ответственность |
|---|---|
| `app.py` | Flask-приложение: страницы, JSON-эндпоинты, webhook Zoom, админка, обработчики ошибок |
| `security.py` | Ключ сессий, CSRF, ограничение попыток входа, проверка `?next=` |
| `database.py` | Подключения (пул для PostgreSQL), схема и миграции, записи, очередь, дедупликация Zoom, пользователи |
| `services/pipeline.py` | Приём Zoom-встреч (`ingest_zoom_meeting`) и обработка записи (`process_record`) |
| `services/background.py` | Фоновые потоки: воркер очереди, heartbeat, возврат зависших задач, поллер Zoom |
| `services/zoom.py` | Zoom REST API и webhook |
| `services/transcription.py` | OpenAI Whisper + ffmpeg |
| `services/llm.py`, `analysis.py`, `detection.py`, `insights.py` | Работа с Claude |

## Модель данных

Таблица `records` (одна строка — одна запись встречи):

| Колонка | Назначение |
|---|---|
| `record_date`, `record_time` | Дата/время начала **по Киеву** (Zoom отдаёт UTC — конвертируется) |
| `record_type` | `lesson` (пробное занятие) или `sales` (продажа) |
| `person_name`, `trainer_name` | Тренер/менеджер; тренер, проводивший пробное (для продаж) |
| `status` | `queued` → `processing` → `analyzing` → `done` / `error` |
| `transcription` | Текст в формате «Спікер: репліка» |
| `analysis_json` | Результат Claude (нормализованный JSON, поле `_kind` = тип анализа) |
| `error_message` | Понятное описание ошибки (раньше ошибка затирала транскрипцию) |
| `source` | `zoom` / `upload` (аудио-файл на диске) / `text` (VTT/TXT загружен в БД) |
| `source_json` | Метаданные Zoom: uuid, тема, длительность, ссылка на запись и т.д. |
| `zoom_meeting_uuid` | UUID встречи Zoom (ключ дедупликации) |
| `job_kind` | `full` (получить транскрипцию + анализ) или `analyze` (только анализ) |
| `auto_detect` | 1 — тип и имя определяет AI; 0 — задал человек (AI не перезапишет) |
| `attempts`, `locked_at`, `not_before` | Очередь: число попыток, heartbeat, отложенный старт |
| `sale_made`, `sale_amount`, `manager_comment` | Ручные отметки руководителя |

Прочие таблицы: `users`, `zoom_processed` (ключи дедупликации: `meeting:<uuid>` и id файлов),
`webhook_log`, `insights_cache`, `app_settings` (сгенерированный ключ сессий, статус воркера).

Миграции выполняются при старте (`init_db`): недостающие таблицы/колонки/индексы создаются
автоматически для PostgreSQL и SQLite; в PostgreSQL DDL сериализуется advisory-lock'ом.

## Жизненный цикл записи

1. **Приём.**
   - Webhook `recording.completed` / `recording.transcript_completed` проверяет подпись
     (HMAC SHA-256), затем `ingest_zoom_meeting`:
     - встречи короче 3 минут пропускаются (в аккаунте много пустых записей на 0 минут);
     - ключ `meeting:<uuid>` захватывается (`INSERT … ON CONFLICT DO NOTHING`) **в одной
       транзакции** с созданием записи: повторные вебхуки, поллер и второе событие о той же
       встрече не создают дублей (раньше M4A и VTT одной встречи давали две записи), а сбой
       посередине не «теряет» встречу;
     - если готовой транскрипции ещё нет — старт откладывается на 15 минут; событие
       `transcript_completed` «будит» ожидающую запись сразу (или повторяет запись, которая
       успела упасть с ошибкой, не дождавшись транскрипции).
   - Поллер каждые 5 минут проверяет записи за последние 3 дня тем же `ingest_zoom_meeting`.
   - Ручная загрузка: VTT/TXT сразу сохраняется как транскрипция (`job_kind=analyze`),
     аудио — на диск под случайным именем (`job_kind=full`).
2. **Обработка** (`process_record`, фоновый воркер):
   - Zoom: свежий список файлов встречи через API → VTT (секунды). Если есть только аудио —
     ждём транскрипцию Zoom до 3 часов после конца встречи, затем Whisper (если есть ключ).
     Скачанное аудио удаляется после транскрипции.
   - После получения транскрипции ставится `job_kind=analyze`, чтобы повтор не платил
     за транскрипцию снова.
   - `auto_detect`: тип по эвристике (длинная основная комната → занятие, короткая
     breakout → продажа), имя — самый активный спикер (без «Audio shared by…» и аккаунта
     «Код Харизми»); в неоднозначных случаях решает Claude.
   - Анализ Claude → нормализация → `status=done`.
3. **Ошибки.** Временные (сеть, 429, 5xx, обрезанный ответ) → повтор через 2 и 10 минут,
   максимум 3 попытки. Постоянные (неверный ключ, запись удалена из Zoom, нет файла) →
   `status=error` с понятным `error_message` и кнопкой повтора в интерфейсе.

## Фоновый воркер и перезапуски

Gunicorn запускает 2 процесса. В каждом стартует поток, но работает только **лидер** —
процесс, захвативший `flock` на `/tmp/maysternia-worker.lock`. Если лидер умирает, блокировку
перехватывает другой процесс (проверка каждые 15 секунд).

Лидер:
- берёт задачи из очереди атомарно (`UPDATE … WHERE id=? AND status='queued'`), до
  `JOB_CONCURRENCY=2` одновременно (бережём память);
- каждая задача сама раз в минуту обновляет `locked_at` (heartbeat — в `process_record`, поэтому
  работает и для `sync_zoom.py --process`); лидер раз в минуту возвращает в очередь задачи без
  heartbeat дольше 5 минут (процесс убит, деплой Railway). Проверено: после `kill -9` лидера
  задача была дообработана другим процессом без участия человека;
- `enqueue` не трогает запись, которая уже обрабатывается (повторный клик → 409);
- при старте удаляет недокачанные/оставшиеся медиафайлы Zoom в `uploads/`;
- пишет свой статус в `app_settings` (видно на странице «Система»);
- запускает поллер Zoom.

Идемпотентность приёма и атомарный захват задач делают систему корректной даже при
нескольких репликах.

## AI

- `services/llm.py`: единый клиент Anthropic (таймаут 600 с, 3 авто-повтора SDK),
  **structured outputs** (`output_config.format` с JSON-схемой) — ответ всегда валидный JSON;
  если модель их не поддерживает — автоматический запасной режим.
- Проверяется `stop_reason`: `max_tokens` (обрезка) → временная ошибка, `refusal` → ошибка.
- Модель задаётся `ANTHROPIC_MODEL` (по умолчанию `claude-sonnet-4-6`).
- Транскрипция передаётся целиком до 300 000 символов (по реальным данным 2-часовое занятие
  ≈ 47 000 символов ≈ 24 000 токенов, 8,5-часовая встреча ≈ 87 000; непрерывная речь — до
  ~50 000 символов/час, т.е. лимит ≈ 6 часов речи); длиннее — начало и конец с пометкой.
- Имя ведущего: VTT Zoom содержит имена спикеров; для текста Whisper (без имён) имя
  определяет Claude.
- `analysis.normalize_*` приводят ответ к схеме (баллы 0–100, допустимые значения шкал),
  поэтому шаблоны и статистика не падают на `null`.
- Аналитика по базе: числовые метрики (выручка, конверсия, средние) считаются в Python,
  Claude даёт только качественные выводы; вход — не более 150 000 символов (текстовые поля
  обрезаются, при нехватке места берутся самые свежие записи).
- Ответ, обрезанный по `max_tokens`, не повторяется (повтор обрезался бы снова).

## Безопасность

- Все страницы и файлы `/uploads/*` — только после входа; отладочные `/debug/*` удалены,
  их функции перенесены на страницу администратора «Система».
- Webhook: подпись HMAC проверяется для всех событий, включая `endpoint.url_validation`
  (иначе ответ на валидацию — это «оракул», подписывающий любые поддельные события).
  Ссылка на запись (`share_url`) принимается только вида `https://*.zoom.us`.
- Идентификатор сессии содержит метку хеша пароля: смена пароля завершает все сессии и
  remember-cookie. Выход — только POST.
- Размер запроса: 2 МБ, для загрузки записи (после входа) — 500 МБ.
- CSRF-токен в каждой форме и в заголовке `X-CSRFToken` у AJAX-запросов.
- Если `SECRET_KEY` не задан или публично известен (был в репозитории), ключ сессий
  генерируется и хранится в БД.
- Cookies: `HttpOnly`, `SameSite=Lax`, `Secure` на Railway; `ProxyFix` для HTTPS за прокси.
- Ограничение: 10 неудачных входов за 15 минут на IP+email и 30 — на email; время ответа
  не выдаёт, существует ли email; проверка `?next=`.
- Заблокированный пользователь теряет доступ сразу; нельзя удалить или понизить
  последнего администратора; удалять записи может только администратор.
- Имена загружаемых файлов генерируются (`uuid4`), путь в `/uploads` проверяется.
