# Аудит и исправления — сентябрь 2026

Проверено: весь код (Python, шаблоны, JS), конфигурация Railway, подключение к Zoom API,
Anthropic и OpenAI, сквозная обработка реальной встречи из Zoom на локальной копии
с PostgreSQL. Все пункты ниже исправлены и покрыты тестами (207 тестов), если не указано иное.

## Безопасность (критично)

1. **Открытые без авторизации `/debug/*`**: любой мог удалить любую запись, прочитать
   транскрипции клиентов, запускать платные AI-анализы, снимать защиту от дублей.
   → Удалены; нужные функции — на странице администратора «Система».
2. **SSRF + утечка токена Zoom**: `/debug/process-vtt` скачивал произвольный URL, добавляя
   к нему OAuth-токен Zoom. → Удалено.
3. **`SECRET_KEY` из публичного репозитория** (значение было записано прямо в старом `app.py`) использовался
   в продакшне → подделка cookie сессии = вход под любым пользователем.
   → Публично известный/слабый ключ автоматически заменяется случайным (хранится в БД).
4. `/uploads/*` (аудиозаписи) отдавались без входа. → Только после входа, защита от `../`.
5. Не было CSRF-защиты. → Токен во всех формах и AJAX-запросах.
6. XSS через имя пользователя в `confirm('…')` на странице пользователей. → Убран inline-JS.
7. Open redirect через `/login?next=https://…`. → Только относительные пути сайта.
8. Заблокированный пользователь сохранял доступ по старой сессии. → Доступ снимается сразу.
9. Нет ограничения попыток входа. → 10 попыток за 15 минут.
10. Скачивание и запуск бинарника ffmpeg из интернета во время работы. → Удалено.
11. «Переглядач» мог удалять записи. → Удаление — только администратор.
12. Нет защиты от удаления/блокировки последнего администратора. → Добавлена.

## Надёжность и данные

13. **Дубли записей**: для одной встречи событие `recording.completed` (M4A) и
    `recording.transcript_completed` (VTT) имеют разные id файлов → две записи.
    `threading.Lock` не работал между 4 процессами gunicorn, где параллельно работали
    4 поллера. → Дедупликация по UUID встречи атомарным `INSERT … ON CONFLICT`.
14. **Потеря обработки при каждом деплое/рестарте**: фоновые потоки убивались; статус
    `analyzing` зависал навсегда, `processing` через 2 часа становился ошибкой без повтора.
    → Очередь в БД с heartbeat; незавершённое возвращается в очередь, до 3 попыток.
15. Ошибка анализа **затирала транскрипцию** (за которую уже заплатили Whisper).
    → Отдельное поле `error_message`; повтор делает только анализ.
16. «Повторить» для Zoom-записи всегда скачивал аудио для Whisper (ключ OpenAI
    недействителен → ошибка), хотя в Zoom есть готовый VTT. → Сначала VTT.
17. `/admin/webhook-logs` и `/debug/zoom-state` падали с 500 на PostgreSQL (`dict(tuple)`),
    на SQLite — из-за `LEFT()`.
18. Кириллические имена файлов: `secure_filename("Запис.m4a")` → `m4a` без расширения →
    Whisper не мог определить формат. → Имена `uuid4().ext`.
19. Кнопка «Скинути» результата продажи записывала «Не продано»; клик «Продано» стирал
    введённую сумму; битый JSON сбрасывал результат или затирал комментарий.
20. **Имена людей**: вместо тренера/менеджера подставлялся email-ник аккаунта-хоста
    («H40904875» / «h40904875» / «Невідомо»), по-разному в вебхуке и поллере.
    → Имя — самый активный спикер в транскрипции Zoom (исключая «Код Харизми»), либо Claude.
21. Дата и время записей хранились в **UTC** (сдвиг 2–3 часа, вечерние встречи попадали
    на следующий день). → Конвертация в Europe/Kyiv.
22. Поллер смотрел 1 день (простой больше суток = пропущенные записи), без пагинации;
    обрабатывал пустые записи на 0 минут (их в аккаунте много) → платные ошибки Whisper.
23. Нарезка аудио: до 50 бесполезных запросов к Whisper на пустые куски; сжатие 64 кбит/с
    давало >25 МБ на час записи. → Один проход ffmpeg с сегментацией, 32 кбит/с моно
    (запасной вариант — FLAC).
24. `.mov` до 24 МБ отправлялся в Whisper напрямую (формат не поддерживается).
25. OAuth-запрос к Zoom без таймаута (мог повесить поток навсегда), новый токен на
    каждый вызов. → Кэш токена, таймауты, повторы при 401/429/5xx.
26. Claude: невалидный JSON или обрезка по `max_tokens` роняли обработку без понятной
    причины. → Structured outputs (JSON-схема), проверка `stop_reason`, нормализация.
27. Сбой определения типа ронял всю обработку записи в поллере; Claude мог вернуть
    недопустимый тип. → Определение не бросает исключений, есть запасная эвристика.
28. Страницы «Статистика», дашборд и запись падали (500) на `null` в анализе.
29. Дашборд загружал полные транскрипции всех записей при каждом открытии. → Не загружаются.
30. AI-аналитика: промпт рос без ограничений вместе с базой; выручку и конверсию
    «придумывала» модель. → Метрики считаются в Python, объём ограничен.
31. PostgreSQL: не было миграций колонок (были только для SQLite). → Общие миграции.
32. `main.js`: без проверки `Notification` на iOS скрипт падал — кнопки на странице записи
    не работали; ошибки сервера молча игнорировались. → Исправлено, ошибки показываются.
33. Загрузка: в диалоге нельзя было выбрать `.vtt/.txt`. Смена типа записи оставляла
    анализ другого типа. → Исправлено; смена типа сама перезапускает анализ.
34. Webhook без `ZOOM_WEBHOOK_SECRET` или без `plainToken` → 500. Некорректный JSON в
    запросах → 500. → Корректные коды 400/401/503.
35. Зависимости без версий (`anthropic>=0.34`, `openai>=2.0`) → непредсказуемые сборки.
    → Версии закреплены.
36. Healthcheck `/login` не проверял БД; 4 процесса gunicorn с дублирующимися фоновыми
    потоками (лишняя память). → `/healthz`, 2 процесса × 4 потока.
37. Мобильная версия: фиксированное боковое меню перекрывало контент.

## Независимое код-ревью (3 ревьюера) — найдено и исправлено

38. **Подделка вебхука Zoom (есть и в старой версии)**: `endpoint.url_validation` отвечал без
    проверки подписи, возвращая HMAC от любого присланного токена — это позволяло получить
    подпись для любого поддельного события и создавать фальшивые записи (в т.ч. со ссылкой
    `javascript:`). → Подпись проверяется для всех событий; `share_url` — только `https://*.zoom.us`.
39. **ffmpeg исчез бы с Railway**: nixpacks ставит `ffmpeg-headless` только при наличии `pydub`
    в requirements. → `pydub` возвращён с комментарием.
40. Встреча могла «потеряться» навсегда, если создание записи падало после захвата ключа.
    → Захват и создание в одной транзакции.
41. «Пул» PostgreSQL с `minconn=0` не переиспользовал соединения (новое подключение на каждый
    запрос, ~40 мс). → Пул держит соединения, проверяет каждое после простоя.
42. Повторный клик «Повторити» мог вернуть в очередь уже выполняющуюся задачу (двойная
    обработка); `sync_zoom.py --process` не обновлял heartbeat. → Условный enqueue (409),
    heartbeat внутри задачи.
43. Токен Zoom попадал в текст ошибки, видимый пользователям. → Вычищается.
44. Смена пароля не завершала существующие сессии/remember-cookie. → Сессия привязана к паролю.
45. Анонимные запросы до 500 МБ (вебхук читал тело в память). → Лимит 2 МБ, 500 МБ только для
    загрузки после входа.
46. Лимит входа сбрасывался перебором 10 000 email; по времени ответа можно было узнать, есть
    ли email; выход через GET. → Исправлено.
47. Мелкие 500: null-байт в `/uploads`, не-строка в имени, JSON-массив/`null` в вебхуке,
    строковые баллы в старых анализах, нестандартные даты (`20260927`). → Исправлено.
48. Текст Whisper (без имён спикеров): фраза с двоеточием становилась «именем». → Проверка
    имени; при отсутствии спикеров имя определяет Claude.
49. Поздняя транскрипция Zoom игнорировалась для записи, уже упавшей с ошибкой; смена типа во
    время анализа терялась; ошибки БД считались постоянными. → Исправлено.
50. Промпт аналитики мог достигать ~400 тыс. символов. → Бюджет 150 тыс.; обрезанный по
    `max_tokens` ответ не повторяется впустую; таймаут соединения с API — 10 с.
51. Прочее: несколько сегментов транскрипции (запись останавливали) склеиваются; остатки
    недокачанных медиафайлов удаляются; гонка миграции SQLite; `lock_timeout` для миграции PG.

Проверено вручную на реальных сервисах: двойное кодирование UUID Zoom работает для всех
видов UUID; миграция со старой продовой схемы PostgreSQL (в т.ч. одновременный старт
нескольких процессов) и работа старой версии на уже мигрированной БД (окно деплоя).

## Что нужно сделать владельцу (нельзя сделать из кода)

1. Задеплоить новую версию в Railway и починить автодеплой — см. `docs/OPERATIONS.md`,
   раздел «Деплой». Railway не выкатывает пуши от GitHub-аккаунтов, которых нет в проекте
   Railway: такой деплой ждёт кнопки **Approve** в списке деплоев сервиса.
2. Задать в Railway уникальный `SECRET_KEY`
   (`python -c "import secrets; print(secrets.token_hex(32))"`). Сейчас приложение само
   заменяет публичный ключ случайным, поэтому после смены ключа всем нужно войти заново.
3. Сделать репозиторий приватным (владелец аккаунта GitHub: Settings → Danger Zone →
   Change visibility) и дать Railway GitHub App доступ к приватному репозиторию.
4. Если нужна транскрипция аудио — рабочий `OPENAI_API_KEY` с балансом (текущий отвечает
   401 `invalid_api_key`: ключ удалён/отозван или из другой организации). Иначе включить в
   Zoom «Create audio transcript»: VTT от Zoom бесплатен и в разы быстрее.
5. Zoom: облачных записей после 29.07.2026 нет. Проверить в Zoom тариф и место под записи,
   настройки облачной записи и кто вёл встречи в августе–сентябре; при нескольких
   организаторах — добавить приложению scope `cloud_recording:read:list_account_recordings:admin`.
6. В старых записях остались даты в UTC и имена вида «H40904875» — их можно поправить
   кнопкой «Редагувати» на странице записи.
